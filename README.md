# AI Context Engineering

> 让 AI 不只“会回答”，而是能在正确口径、正确数据和可验证证据上完成分析任务。

## 项目判断

企业分析场景里，模型能力往往不是主要瓶颈。真正影响交付质量的，是 AI 能否找到正确的指标口径、识别需要的数据、调用合适的查询，并在下结论前完成交叉验证。

这个项目用一个脱敏模拟问题演示上下文工程：

> 昨天华北区销售额为什么下降？

第一版只是把表格交给模型总结；升级后，系统把业务文档、指标定义、查询工具、分析规则和验证步骤组织成一条可追踪链路。

## 从“给更多上下文”到“组织可执行上下文”

| 第一版做法 | 主要风险 | Context Engineering 做法 |
| --- | --- | --- |
| 一次性塞入大量资料 | 噪声多、来源不清 | 按问题检索最小必要上下文 |
| 直接让模型解释波动 | 相关性被写成因果 | 先拆指标，再逐项取证 |
| 只查询一次 | 异常可能来自口径或延迟 | 主查询 + 交叉验证查询 |
| 给出流畅结论 | 无法回看证据 | 结论逐条绑定证据与置信度 |

## 上下文架构

```text
用户问题
  ├─ 业务定义：区域、时间、销售额口径
  ├─ 数据上下文：日报快照、活动日历、数据新鲜度
  ├─ 工具上下文：可调用查询及参数约束
  ├─ 分析规则：先量级、再拆分、后归因
  └─ 输出约束：结论、证据、风险与下一步
          ↓
    查询 → 解释 → 复核 → 交付
```

## Demo 展示什么

页面不是聊天框，而是一张分析工作台：

- 左侧固定用户问题、任务范围和数据边界；
- 中间逐步回放“理解—检索—查询—拆解—验证”；
- 右侧只展示已被证据支持的结论，并保留不确定性；
- 点击步骤可以查看输入、工具调用和产出，点击“重新回放”可观察完整链路。

本项目中的公司、区域和经营数字均为脱敏模拟数据，只用于说明产品方法。

## 验证闭环

1. **口径检查**：确认“昨天”“华北”“销售额”的定义。
2. **量级检查**：先确认下降是否超过日常波动范围。
3. **结构拆解**：按城市、流量、转化率与客单价拆分。
4. **事件核对**：匹配活动变化和数据延迟信息。
5. **反证查询**：检查其他区域及退款因素，避免单点归因。
6. **证据门槛**：证据不足时输出“待验证”，不生成确定性结论。

## 我的工作

- 把模糊经营问题拆成口径、数据、工具、规则和输出五类上下文；
- 设计查询前检查、指标拆解与二次验证流程；
- 设计可回放的执行轨迹，让产品和技术角色能共同审查结论；
- 用“证据是否足够”控制结论强度，而不是用语言流畅度掩盖不确定性。

## 项目边界

这是一套用于求职展示的脱敏重构，不连接真实公司数据、权限系统或生产查询引擎。Demo 中的工具调用由确定性样例驱动，重点展示上下文组织、验证机制和产品判断，而不是宣称已建设生产级数据平台。
